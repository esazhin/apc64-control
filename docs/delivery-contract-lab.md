## 0 · Sections guide — how to read this document

This contract is the agreed scope of one delivery: what will be built, how it will be judged, and the
design the build follows. **§1–§5 state the agreement** — the problem, the solution direction and the
properties it guarantees, the working context, the plan with its acceptance criteria, and the runbook.
**§6–§7 are the derived build plan and binding design**; **§8 is appended when the delivery completes.**

A build that WALKS this contract reads five forms out of it, and reads nothing else about its
structure. They are prose within the frozen headings and table columns below; a contract missing one
is returned to review naming the row rather than half-planned.

1. Section role. Directly under a heading, one line `Role: binding — <why>` or
   `Role: informational — <why>`. Binding sections are carried to the builder IN FULL; informational
   ones are carried by pointer only. A contract stating no roles gets the default binding set
   (§2.5, §3.5, §4.2, §6.1, §7, §7.2) and a loud note that the default was used.
2. Task-row ownership. In §6.1's `design_refs` column: `OWNS: <paths>; TOUCHES: <paths>;
   BINDS: <seam>:<from|to>, …; DISCHARGES: <acceptance ids>; WIRES: <seam ids>` — semicolon-separated,
   any clause omitted when empty. This is where a seam SIDE is attached to the task that owns it;
   free-prose name matching across the §7.2 from/to columns is not a substitute. `WIRES` names the
   seams a task composes (both of their sides this design's): its piece proves each is wired.
3. Acceptance-row identity. In §4.2's first column: `<row id> · <sub-outcome id>` — the row's OWN
   stamped id first, then the sub-outcome it realizes. Several rows share a sub-outcome; only the
   row id can be discharged by exactly one task.
4. Artifact line. In §7's `layout`, one line per module: `` - `path` — responsibility — layer: <layer> ``
   where layer is one of contract / domain / application / infrastructure / wiring / presentation / edge / document.
   The layer is what orders the build inward-first.
5. Size bound. In §7, one line `Size bound: <n> artifacts per unit.` — a task row naming more splits
   mechanically, each split keeping its own seam sides and acceptance rows.

Reviewing: **§4.2 (Acceptance) and §7.2 (Seams) are the heart** — every §4.2 row is an observable
behaviour the delivery must demonstrate, and every §7.2 row is an internal connection a test must
actually execute. Place corrections at the specific row or clause they concern — the section structure
itself is fixed.

## 1 · Intent
Role: informational — the problem and its why; the builder is aware of it and never acts on it.
- **outcome:** The user plays their Akai APC64 as an expressive instrument for theory and harmony work, and already has a working Linux host for it (contract 1, the APC64 Host). The user now wants a layout lab and live harmony views on top of that host. LAYOUT LAB: harmonic pad layouts are generated, not hand-programmed. Examples are Tonnetz on a staggered checkerboard, isomorphic layouts and colour schemes, and the generators must be easy to extend. They are played in the unit's own Custom view, because only there do all 64 pads carry the generated notes and colours and play with real velocity and per-pad aftertouch. Switching between generated layouts is instant. While playing, the user moves the window across the lattice from the unit: each encoder click shifts it one step of the current interval, Tempo cycles the interval (octave, fifth, third), and the OLED shows the layout, interval and offset. Shift plus encoder stays the host's layout browser. HARMONY VIEWS: they show what the user plays, live: a pad replica, a Tonnetz lattice with triads, chord names with a trail, single-note interval and neighbouring-chord hints, and a circle of fifths. PROJECT MEMORY: the unit's 24 stored projects can be backed up, restored and pushed to a slot. There is a layout library, and Akai Project Editor .APC64 files can be imported. Nothing on the unit is ever overwritten without an automatic backup first. GLOBAL SETTINGS: the unit's global settings (CV/Gate sources and channels, drum notes, LED level, sync, device mode) can be read and changed, with a backup first. As with the host, the user builds and changes things mainly by asking an AI agent, so everything must be agent-operable: high-level validated definitions, a schema and a worked-example guide, precise errors, and the same CLI and HTTP API as the page. The browser is for seeing, playing, switching and light tweaks. It is the same page as the host (a panel on port 5058, no login), and it must make the lab discoverable the way the host page does.

### 2.2 Summary
- **summary:**
  Turning the encoder moves the Tonnetz or isomorphic window on the pads instantly, and Tempo changes the step between octave, fifth and third.
  The unit's projects and global settings are always backed up before anything on the unit is overwritten.
  If a write to the unit goes wrong, the previous state is put back and the OLED and page say so.
  Every lab action works the same from the agent, the command line and the page.
  New layout generators and colour schemes can be added without touching the host.

### 2.3 Ideality — what it optimizes for / deliberately trades
- **Optimizes for:**
  Turning the encoder or pressing Tempo in a generated Custom-view layout re-colours and re-notes the 64 pads within about 50 ms of host processing, even during fast spins.
  Every 0x14 project write and 0x18 global-settings write reaches the APC64 only through the one backup → merge → write → read-back pipeline. The gate refuses and logs every other such frame.
  Bytes nobody understands yet in pad, strip and global records are carried through every write unchanged.
  Backup all, restore a slot, push to a slot, import a .APC64 file and change a global setting are each one validated command, the same on the CLI, the HTTP API and the page.
  Adding a new layout generator or colour scheme is one new file plus its test, with no change to the _apc64_host core.
- **Deliberately trades away:**
  Within a lab session, slot 0 is not backed up before each encoder click. One backup taken before the session's first write covers every shift, and is restored at session end.
  Read-back after a window shift is checked just after the write, not before the pads change. A mismatch is undone after the fact, not prevented.
  Intermediate window positions during a fast encoder spin are skipped. Only the latest position is written.
  Device-mode and sync changes cost one extra explicit confirmation, even when the agent asks for them.

### 2.6 Assumptions
Scales: **importance** = impact if the assumption is false (0 = none → 10 = the delivery is impossible as contracted) · **uncertainty** = what is actually known (0 = a known fact or proven → 10 = no clue, and the truth may be the complete opposite). A sum ≥ 17 is either **resolved** (settled before this contract shipped — the evidence is in `resolution`) or **escalated** (only the stakeholder can settle it: it is NOT a fact, it is listed under §1 to validate first, and its last column gives the easiest way to validate it and what changes if it is false). Rows `q…` are the answers this design assumes to points the stakeholder can decide; one the stakeholder answered is resolved by that answer. Rows `d…` sweep the terms of the ask: one row per class a term admits, its `kind` the lens it was found through (`quality` for a quality word's measure); a forced class is resolved by the reasoning in `resolution`, followed by what settles it outside this design (`source:` a definition, common knowledge, a repository path, the run environment, a prior, or the ask's own words quoted), a chosen one states the treatment this design picks and is graded like any other row.

## 5 · Execution notes
The build proceeds in this order: verify the §2.1 priors first (especially any linchpin), orient in the
§3 context and the repository's own docs, then realize each §4.1 leaf — tests first, implementation,
its §4.2 acceptance as the gate — checking change impact before edits and reusing what exists rather
than rebuilding it. Work outside the executor's reach is flagged, never silently skipped; the outcome
is self-reported to §8.

  StripRecord (14 B kept whole)

  Confirmation (explicit; its absence means refusal for Hazard fields)

  UnitView (SESSION, NOTE, CHORD, DRUM, STEP, PROJECT, CUSTOM)
  HeldNotes (multiset), Chord (root, suffix, bass; label), Triad (root, MAJOR | MINOR; neighbours), ChordTrail (≤ 8), HarmonyState (snapshot)
  ModuleAction (module, action name) — host binding kind
  WriteCapability — host token type, one instance
  LayoutIssue (reuse host: file, line, field, problem, fix)

- **dependency direction:** Dependencies point inward only. `_apc64_lab/domain` imports only the stdlib and `_apc64_host` domain value types (midi, oled, issues, outbound token), never I/O, FastAPI, ALSA or files. `_apc64_lab/application` imports lab domain and `_apc64_host/application/ports.py` Protocols only, never infrastructure or presentation. `_apc64_lab/infrastructure` implements lab ports and uses the host gate and session tap. `_apc64_lab/presentation` imports lab application (and implements LabStatePublisher over ws_hub). `_apc64_lab/composition.py` is the only lab file that constructs adapters. ### 7.1 Design decisions
| decision | principle preserved |
|---|---|
| `_apc64_lab/application/guarded_writer.py` is the only issuer of 0x14/0x18. It holds the single WriteCapability, and every command write runs read → backup → merge → unchanged? → write → read-back → roll back. | SRP plus intermediary-enforced integrity (inv1, inv2, inv4): structural, not by discipline |
| `_apc64_host/application/outbound_gate.py` passes capability-scoped commands only with the token, refuses and logs every other 0x14/0x18, and is otherwise unchanged for contract 1. | OCP (additive seam) and DIP (policy injected) |
| `_apc64_lab/domain/records.py` merges only the fields the lab sets (with_pads/with_change), and keeps every unknown pad, strip and global byte. | Value object with invariant-preserving mutators (inv3) |
| `_apc64_lab/domain/session.py` takes one session backup before the first slot-0 write, and `_apc64_lab/application/session_service.py` restores it on end, release, stop or unload after comparing slot 0 with the last written record. | Aggregate root owns the session invariant (inv5, inv6) |
| `_apc64_lab/application/session_service.py` Slot0Writer is latest-wins and paced on the previous write's transmission only. It verifies by read-back after the burst settles, and coalesces while a command holds GuardedWriter's lock. | SRP (pacing separated from the domain decision) |
| `_apc64_lab/domain/lab_section.py` compiles the layout's 'lab:' section into the base-layer encoder/tempo ModuleAction bindings, so the active layout is the single owner of those controls. Shift + encoder stays host navigation. | Single source of truth and DIP via HostModule.actions() |
| `_apc64_lab/domain/generators.py` defines PadLayoutGenerator/ColourScheme protocols, and `_apc64_lab/generators/__init__.py` is the plugin directory. A new generator or scheme is one file. | OCP and ISP |
| `_apc64_lab/domain/memory_sysex.py` and `_apc64_lab/domain/apc64_preset.py` keep each build/parse pair together, with golden round-trips against the fixtures. | Emit/parse inverse pairs co-located (anti-pattern 5) |
| `_apc64_lab/domain/memory.py` types slots, backup targets and outcomes, so slot 25, a push to slot 0 or an unconfirmed device-mode change cannot be typed. | No primitive obsession; impossible states unrepresentable |
| `_apc64_host/application/engine.py` implements NoteEnder, which also publishes 'ended by window shift' note-offs on the play stream, so the views and the activity list stay true. | One event source for played state (inv15) |
| `_apc64_lab/application/harmony_tracker.py` computes HarmonyState server-side from the play stream, and `_apc64_lab/presentation/publisher.py` pushes it on the ws 'lab' topic with snapshot-on-connect. | DIP (application port, presentation adapter); agent-operable state through the same API |
| `_apc64_lab/application/guarded_writer.py` refuses memory writes unless the held unit's firmware equals `_apc64_host/protocol/sysex.py` KNOWN_FIRMWARE. | Single source for a shared constant (anti-pattern 4) |
| `_apc64_host/application/tweaks.py` save_section_field writes lab tweaks through notation/splice.py, and the host hot reload re-activates the layout. | Reuse plus emit/parse pair (lab_section parse ↔ splice emit) |
| `_apc64_lab/composition.py` builds every lab object by constructor injection, and `_apc64_host/__main__.py` is the only host file that names the lab. | Clean architecture: composition root, no singletons |

### 7.3 Seam clauses
Role: binding — each seam's contract, clause by clause: an expectation is what the consumer sends, which the supplier must accept; an answer is what the consumer relies on getting back, and when. Every clause is proven on both sides — by the consumer's test over a double and by the supplier's test of the real thing. Where the supplier is a third party outside the design, our side is the test of how we USE it, and its side is the clause's `basis`: `documented: <where its documentation says so>`, `assumption <a §2.6 id>` (relied on, not guaranteed — validated as its grade says), or `customer-ci` (a supplier the customer's organisation owns, whose CI runs our consumer contract). Clauses whose supplier is in this design leave `basis` empty.
